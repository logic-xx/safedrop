# SafeDrop：运行与验收

SafeDrop 是一个支持加密文件传输、断点续传、公钥认证、会话控制和可校验审计的 Web 项目。本文介绍本地运行、容器部署和安全验证；协议与边界见《协议与安全设计.md》。

## 1. 本机启动

需要 Node.js 24.14 或同一主版本的后续版本、npm 和 OpenSSL。首次运行在项目目录执行：

```powershell
npm ci
npm run setup
npm run build
npm start
```

然后访问 **https://localhost:8443**。

- 初始化会生成 `admin`、`alice`、`bob` 三个账号，分别用于管理员、普通用户、VIP 用户。每次新环境的口令随机生成，保存在 `.local/accounts.json`。请在本机自行查看，不要公开该文件。
- 初始化不会覆盖已存在的账号、文件或证书。
- 本地 CA 公共证书位于 `.local/tls/ca.crt`。浏览器首次使用前，需要由使用者核对来源后将这个证书导入当前用户的受信任根证书存储。不要导入 `ca.key`；不要通过关闭证书验证来使用程序。
- CA 私钥和服务器私钥在 `.local/tls/`，已排除在 Git 和镜像构建上下文之外。该目录应仅供部署维护者访问。
- OpenSSL 不在 PATH 时，可先设置 `$env:OPENSSL_PATH='实际的 openssl.exe 完整路径'`。
- Node.js 24 的内置 SQLite 仍会显示 API 尚未稳定的提示；当前代码已在 v24.14.0 实测。升级 Node 主版本前需重新测试。

口令登录后，可在“安全中心”重新输入口令并绑定本机公钥。以后同一浏览器可使用公钥登录。私钥通过 IndexedDB 保存为不可导出的 CryptoKey，清理浏览器数据或更换设备后需要重新绑定。撤销公钥与撤销已登录会话是两个独立操作；必要时分别执行。

## 2. 文件传输

- 同时选择多个文件即可创建任务，界面最多并发运行三个任务。上传与下载共用同一条 WSS 连接及账号总速率额度。
- 上传中断后，可在重新登录后重新选择相同文件继续。服务端校验名称、大小、完整文件摘要与任务所有权。界面可取消未完成任务以释放配额。
- 下载续传推荐桌面 Edge/Chrome，并允许用户选择本地目标文件。每 4 MiB 提交一次磁盘检查点，正常暂停或可处理的断线会提交当前位置；浏览器异常终止时通常只能恢复到最后一个已提交检查点。
- 本地下载文件重新授权后，客户端计算已有前缀摘要，服务端核对后才接受续传位置。不能恢复到未保存或内容不一致的位置。
- 其他浏览器保留 32 MiB 以内的普通下载；不声称具备相同的磁盘续传能力。
- 默认单文件 512 MiB，每账号总文件与未完成上传预留空间 1 GiB，最多 16 个未完成上传、1000 个已完成文件。普通/VIP 速率分别为 1/4 MiB/s，双向合计，允许首块突发。

## 3. 自动验证与报告

```powershell
npm test
npm run security:report
```

前者运行协议、账号聚合限速和真实 TLS/WSS 集成测试；后者独立启动隔离测试服务并输出：

- `reports/latest.html`：可直接打开阅读的报告。
- `reports/latest.json`：机器可读结果，管理员在“审计与验证”中刷新后可查看。

测试使用 `tmp/` 下的独立目录及临时账号，不读取真实账号口令，不对外部服务发起压力流量。测试目录中可能有临时凭据和证书，不应提交。测试只覆盖列出的场景，并非完整安全审计。

## 4. 审计日志独立校验

管理员可在界面导出日志及检查点。将检查点保存到服务器以外的位置，然后运行：

```powershell
npm run audit:verify -- 日志文件.json 独立检查点.json
```

校验工具检查序号、前驱摘要、当前摘要以及检查点是否匹配。修改日志副本后可重复验证；切勿为了演示修改真实运行数据库。没有独立可信检查点时，只能证明日志链内部一致，不能证明历史没有被整体重写。若攻击者同时控制日志、检查点与验证工具，当前方案不提供可信保证。

## 5. 本地容器部署

需要已正常启动的 Docker Desktop Linux 引擎；配置文件本身不能代替安装和启动容器引擎。

```powershell
docker compose config --quiet
docker compose up --build -d
docker compose ps
docker compose cp gateway:/data/caddy/pki/authorities/local/root.crt .local/container-ca.crt
```

由使用者核对并信任导出的 **容器本地 CA** 后，访问 https://localhost:8443。本地容器的 CA 与本机直接运行模式的 CA 不同。`docker compose exec app cat /data/accounts.json` 可在自己的终端查看容器随机账号，请勿将输出用于公开截图。

本机直接运行与容器部署会占用同一个 8443 端口，应先停止其中一个。停止服务使用 `docker compose down`；不要附加删除数据卷的参数，除非确定要销毁持久化数据。

容器部署设计：

- Caddy 网关只向本机映射 8443，使用自己的本地 CA；应用服务不映射宿主机端口。
- 应用进程 UID/GID 为 10001，根目录只读，只有数据卷及受限临时目录可写。
- 业务容器移除全部 Linux capabilities，并禁止提权；设置内存、CPU、进程数上限。
- 网关的 `/data` 与 `/config` 持久化保存其证书状态，网关也配置只读根目录与资源上限。
- 后端网络标为 internal；应用数据使用命名卷，报告目录只读挂载。网关同时连接 backend 和独立的 edge 入口网络，以便发布本机 HTTPS 端口；业务容器仅连接 backend。网关不能只连接完全隔离的 internal 网络，否则可能无法创建实际端口映射。参见 [Docker Compose 网络说明](https://docs.docker.com/compose/how-tos/networking/#internal-networks)。
- HTTPS/WSS 在网关终止，网关到同一宿主机的应用走隔离 Docker 内网 HTTP/WS。当前威胁模型信任容器宿主机，不声称容器内部这一跳也是 TLS。面对不可信容器网络时需增加后端 TLS/mTLS。
- 源码和凭据不会通过 Docker socket 暴露给应用。容器隔离不替代每次文件操作的用户授权。

独立容器验收可在普通 PowerShell 中执行：

```powershell
.\scripts\verify-container.ps1
```

前提是已安装本地 Node.js 依赖（`npm ci`）且 Docker Desktop 的 Linux 引擎已就绪。脚本合并 `compose.yaml` 与 `deploy/compose.verify.yaml`，使用独立的 `safedrop-check` 项目与数据卷，只向本机映射 `18443` 端口。Compose 的 `!override` 语法要求 v2.24.4 或更高版本。可以先执行 `-CheckOnly` 检查合并配置及本地依赖，此模式不访问引擎。

完整流程会构建并启动容器，核对非特权应用账号、只读根目录、capabilities、禁止提权、CPU/内存/PID 上限和网络隔离；同时要求实际网关端口映射只能是 `127.0.0.1:18443`，并检查网关拥有独立入口网络。随后通过严格校验证书的 HTTPS/WSS 完成上传、下载、摘要校验及跨用户拒绝测试。脚本保留一个部分上传及独立审计检查点，重启两个容器后检查账号、CA、已完成文件、上传确认偏移及审计历史是否保留。

只有全部步骤成功才生成 `reports/container-latest.json`。该结果与 `reports/latest.json` 中的应用集成测试结果分开记录。新验收开始前会清除上一次容器验收报告，以免失败后误读旧的成功结果。`reports/container-runtime.json` 只记录用户编号、网络及端口映射等非凭据信息，供失败时诊断。运行日志可能包含平台诊断信息，账号文件和 CA 公共证书保存在 `.local/container-check/`，不打印口令，也不修改系统证书信任。

脚本完成后保留验证容器及数据，方便人工检查。停止时执行：

```powershell
docker compose -p safedrop-check -f compose.yaml -f deploy/compose.verify.yaml down
```

**当前验证状态**：2026-11-13 已在使用者终端完成 Linux 镜像构建，应用和网关均通过启动等待检查。首次完整验收在网关未发布端口处停止；本机 HTTPS 连接也被拒绝。已为本地网关补充 edge 入口网络，并增加配置预检与实际网络检查，待重新运行脚本后验证 HTTPS、文件传输及容器重启恢复。自动执行环境访问 Docker 命名管道仍返回 permission denied，涉及引擎的步骤需在具备访问权限的普通终端执行，实际结果以新生成的报告为准。

## 6. 公网部署与 Let's Encrypt

提供独立的 `compose.public.yaml`，不会默认发布到公网。具备实际受控域名和服务器后，设置 `DOMAIN`、`ACME_EMAIL`，检查域名解析及 80/443 可达，再执行：

```powershell
docker compose -f compose.public.yaml config --quiet
docker compose -f compose.public.yaml up --build -d
```

此配置的 Caddy 明确使用 Let's Encrypt ACME 端点自动申请、续期服务器证书。公网配置与本地配置使用不同项目数据卷。首次调试应采用 ACME 测试环境，测试证书不受浏览器默认信任；正式演示使用生产证书。尚未申请或验证任何公网证书。

首次对外发布前，应完成容器实测、改进账号管理与恢复流程、配置审计归档及全局磁盘监控。当前按 IP 的限制在代理后会合并为网关地址，属于保守的全站限制；如需准确识别来源，应仅信任已验证网关设置的转发地址。

## 7. 验证范围与当前限制

- 已通过 TypeScript 与 Vue 检查、生产构建，以及编译后的 HTTPS 服务启动、主机名校验和安全响应头检查。
- 独立验证工具覆盖 28 项 TLS/WSS 集成场景，另有密码学互操作、协议长度和账号聚合限速检查。输入和断言见 `tests/`，实际结果见 `reports/`。
- 浏览器已验证登录、工作台导航、会话展示、审计链校验及报告展示。文件上传、原生磁盘保存与恢复、公钥设备绑定仍需补充完整人工验收。
- 本地界面测试使用独立的临时账号与数据，明确显示“本地界面测试”；部署入口使用 HTTPS/WSS。页面退出后连接管理器不会继续作为独立进程运行。
- 容器镜像启动及公网证书签发尚未在当前环境实测。当前版本尚不具备完整的用户自助管理与账号恢复流程，公开部署前需完善这些能力。
- 限流和资源限制覆盖部分应用层拒绝服务场景。链路饱和需要上游防护；审计归档、全局磁盘监控、写入失败和浏览器异常退出仍需专项验证。
- 上传恢复实测覆盖进程重启。文件 sync 与数据库记录共同确定确认偏移，不宣称对所有断电或硬件故障均提供恢复保证。
- 可校验审计依赖独立可信检查点；它不提供日志永远不可篡改的保证。
