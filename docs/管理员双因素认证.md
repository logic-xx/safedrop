# SafeDrop 管理员双因素认证

版本：11 最小版，2026-11-18。仅管理员可自行启用，升级不会自动改变已有账号的登录要求。普通用户仍使用原口令或公钥登录。实际测试状态分别见[验证记录](验证记录.md)、[浏览器验收清单](浏览器验收清单.md)和[安全验证矩阵](安全验证矩阵.md)。

## 1. 启用与登录

管理员进入“安全中心”的“管理员双因素认证”，输入当前口令并开始绑定。在自己的验证器中选择手动输入密钥：服务为 SafeDrop，账号使用页面所示账号名，类型为基于时间的六位验证码。点击复制密钥，仅粘贴到自己的验证器；不要把密钥放进聊天、截图或仓库。本版提供手动密钥绑定，不调用外部二维码服务。

输入新验证器的六位验证码，勾选确认，再启用。准备阶段不会启用 MFA；绑定只在当前连接内有效，五分钟到期、取消、退出或断线后需重新开始。成功后立即安全保存十份一次性恢复码，与账号口令分开保管；只展示本次，隐藏、离开或刷新后不能重新读取原文。若未妥善保存，应在仍可使用验证器时更新恢复码。

启用后的管理员使用“口令 + 验证器验证码”登录。口令正确后只是进入第二步，不返回业务会话；第二步绑定该连接和身份版本，两分钟内完成。旧公钥登录不能替代口令或验证码，已开启 MFA 的管理员不再绑定新公钥。旧公钥已从服务端撤销，浏览器持有的旧私钥不会被远程擦除。

验证码按 [RFC 4226](https://www.rfc-editor.org/rfc/rfc4226.html) / [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html) 使用 HMAC-SHA-1、六位数字、30 秒时间步；允许服务器当前步及前后各一步，已成功使用的时间步不能再次使用。启用时的验证码也会消费；紧接着重新登录或执行敏感操作时，请等验证器显示下一组新码。部署主机与验证器的时间应保持准确。本功能不提供 Passkey 或抗钓鱼保证。

每账号在五分钟窗口内累计五次失败后锁定五分钟，计数持久化，换连接或重启不解除；每个登录第二步最多五次提交，另有每 IP 五分钟 30 次保护。代理后 IP 计数仍按现有保守方式合并；频率保护和会话协调按单应用进程设计。

## 2. 恢复、轮换与停用

遗失验证器时，在口令验证后的页面选择恢复码，输入一份未使用的码。恢复码本身不能代替口令，也不会直接关闭 MFA。恢复会话最长五分钟，只允许读取自己的 MFA 状态、重新绑定、取消绑定和退出；文件、用户管理、维护、审计导出、改密和停用 MFA 等业务操作均拒绝。

重新绑定时再次核验当前口令，添加新密钥并通过新验证码确认，才恢复完整会话。原 TOTP 密钥和剩余旧恢复码失效，重新生成十份恢复码。输入过的恢复码持久化消费，其他连接和重启后都不能重用。若验证器及所有恢复码均丢失，本版没有管理员代重置或绕过 MFA 的入口；应联系部署维护者评估已保管的验证器、恢复资料和可信备份，不能直接删表关闭保护。仅恢复数据库并不保证恢复登录能力。

正常完整会话可以更新恢复码或停用 MFA，两者均需当前口令、一个未使用的验证码和明确确认。更新后旧恢复码全部失效。停用后允许仅凭口令登录，属于降低认证要求，应由账号本人确认；旧公钥不会恢复。

启用、重新绑定、更新恢复码和停用都会增加身份版本，撤销其他会话及已绑定公钥；当前完成敏感验证的会话保留。正在等待的其他会话传输会中断，文件与续传任务保留。修改口令继续撤销全部会话和公钥，同时保留已启用的 MFA 与恢复码状态；停用账号阻止未完成的第二步登录。所有状态变更和对应审计一起事务提交，审计失败时不产生半提交的认证状态。

## 3. 密钥与存储

SQLite 从版本 4 增量迁移至 **版本 5**，只新增 `mfa_settings`、`mfa_recovery`、`mfa_sessions`、`mfa_attempts` 四张表。原账号、口令散列、公钥、文件、任务、授权、活动时间和审计行不改写。原有进程会话仍按启动规则撤销，不清库或重建数据卷。

TOTP 密钥以 AES-256-GCM 加密，认证附加数据绑定账号标识；密文不能移植到另一账号。恢复码为每份 128 位随机值，只持久化绑定账号的 SHA-256 摘要。登录只在验证、一次性消费、会话因子记录和审计全部提交后建立会话；审计失败不会提前消费正确验证码或恢复码。

部署加密密钥通过 `MFA_KEY_FILE` 配置，默认是 `DATA_DIR` 加 `.mfa-key`：

| 环境 | 默认路径 |
| --- | --- |
| 本机 | `.local/data.mfa-key` |
| 容器 | `/data/store.mfa-key`，保留在现有应用数据卷中 |

首次启用时排他创建 32 字节随机密钥文件并同步落盘；POSIX 文件模式为 0600。文件必须与业务数据目录和备份目录隔离，拒绝放在 `objects/` 或备份目录中，拒绝符号链接文件及错误长度。Windows 实际权限仍依赖运行账号和 ACL。启动时已存在启用记录而密钥缺失、错误或密文认证失败，会拒绝启动，不自动取消 MFA。

数据备份保留加密的 MFA 配置和已消费状态，**不包含部署加密密钥**。部署维护者必须把正确的 `.mfa-key` 单独保存在受保护介质或独立保管位置；不要公开、打印或提交这个文件。仅有数据库备份不足以恢复已开启 MFA 的账号。同一 OS 账号下的两个目录不自动构成权限隔离，仍信任部署宿主机。

隔离恢复时，先按[存储维护与恢复](存储维护与恢复.md)恢复到不存在的新数据目录，再提供对应部署密钥：可将受保护副本放在新数据目录外并设置 `MFA_KEY_FILE`。不要生成新随机密钥覆盖原密钥；不要把缺失密钥当作停用双因素的理由。备份格式、原审计链段及既有检查点机制保持不变。

## 4. 维护工具

管理员已启用 MFA 后，本机维护工具也必须完成第二步。将当前六位验证码写入受保护的本地短期文件，再通过文件路径传入，避免验证码直接出现在命令参数或终端历史中：

```powershell
npm run maintenance -- status --origin https://localhost:18443 --ca .local/container-check/ca.crt --accounts .local/container-check/accounts.json --otp-file .local/admin-otp.txt
```

`backup` 和 `anchor` 同样支持 `--otp-file`。文件只放当前验证码，不放 TOTP 密钥或恢复码；已使用的验证码不能在下一次命令中重用。账号资料文件仍需使用有效口令，改密后初始化文件不会自动更新。CLI 不接受恢复码建立维护权限，受限恢复只能重新绑定验证器。

`anchor --interval-seconds` 完成一次认证后复用同一条已验证连接，不会每分钟重新使用同一验证码。会话到期、连接失败或进程重启后需重新认证，不能把它当作永久授权的无人值守守护服务。

版本 7 容器验证脚本新增 `tests/container-mfa.mjs`：在最终镜像内的全新 `/tmp` 目录创建专用账号，验证启用、口令阶段拒绝业务、验证码重放、正确登录、受限恢复、重新绑定及重启持久化。该进程仅使用容器内回环 HTTP/WS，外部 HTTPS/WSS、证书及主机名仍由原容器验收独立严格检查；不更改现有 admin/alice/bob 的 MFA 设置，也不额外发布端口。

原容器验收所用的管理员若已自行开启 MFA，旧的仅口令自动登录不会被豁免，需由维护者安排有效的第二步凭据或人工验收；不得为跑脚本关闭 MFA。此次开发验收不自动开启原容器管理员的 MFA。

## 5. 证据与边界

`tests/mfa-unit.test.ts` 对照 RFC 公布的 HOTP/TOTP 向量；`tests/mfa-suite.ts` 使用独立 TLS/WSS、临时账号和磁盘，覆盖权限、绑定期限、重放、持久化锁定、旧公钥、恢复权限、重新绑定、轮换、停用、改密/停用联动、审计回滚、独立密钥恢复和增量迁移；维护 CLI 另有真实调用检查。

自动、编译版、浏览器实际点击、使用者完成的凭据确认、实际 Docker 容器结果分别记录。编译版在宿主机通过不等于最终容器已通过；未观察的绑定或停用点击不标为浏览器成功。当前状态见[验证记录](验证记录.md)。

本版不提供短信、邮件验证码、二维码扫描、WebAuthn、管理员代重置、密钥轮换工具或多进程协调。用户需妥善保存验证器及恢复码，部署者需保护并独立备份加密密钥。认证会话被盗、浏览器或宿主机已被控制等情形仍依赖其他保护；本功能不构成全面安全认证。恢复路径的设计参考 [OWASP MFA Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)。
