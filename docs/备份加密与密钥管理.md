# SafeDrop 备份加密与密钥管理

2026-11-18，第 2 阶段（08 增强）候选已实现，宿主机回归和独立 Edge 界面通过；本轮实际 CI、最终镜像及版本 9 原卷升级尚待验证，未宣布整阶段完成。当前运行容器仍是已验收的 `068ee92`，版本 8 证据不替代新功能验收。具体报告和边界见[验证记录](验证记录.md)。

新服务端备份一律使用独立于 MFA 的随机 256 位密钥，默认路径为 `DATA_DIR` 加 `.backup-keys`，允许部署者指定 `BACKUP_KEY_FILE`。部署维护者通过本机 CLI 初始化及轮换，界面只显示可用状态、密钥编号和副本格式，不返回密钥。服务启动不自动生成备份密钥。初始化不覆盖已有文件；轮换原子写入且保留所有旧密钥，最多 32 个，拒绝并发写入，不提供自动删钥。密钥须在业务目录和备份目录之外，也不能使用 MFA 密钥路径；拒绝符号链接文件及不安全权限。Unix 文件模式为 0600，Windows ACL 由运行账号及部署者保护。

没有可用密钥时，只拒绝新备份，不生成明文替代副本，也不关闭原有文件服务。旧明文副本保留，离线校验/恢复需显式选择旧格式兼容；新加密格式不能通过修改版本号降级成已认可的明文副本。

格式 2 使用 Node 标准库的 HKDF-SHA-256 和 AES-256-GCM，不新增加密依赖。每份备份生成 32 字节随机盐，以 `SafeDrop backup v2/` 加备份编号作为 HKDF info，派生独立的 32 字节密钥。清单使用序号 0、条目使用 1～100000；nonce 为 12 字节，前 8 字节为零、后 4 字节为大端序号，同一写入上下文拒绝重用序号。附加认证数据按 JSON 数组绑定版本、方案、备份编号、创建时间、密钥编号、盐、序号、逻辑路径，使用完整 128 位认证标签。单条目明文上限为 `2^36−32` 字节，约 64 GiB；应用文件大小及备份预算还会另行限制。

根目录只含 `manifest.json` 与 `sealed/`。外层清单包含格式、编号、时间、密钥编号、盐、密文字节总数及加密内层清单；条目保存为按序号命名的 `.bin`，认证标签附在各密文末尾。内层清单包含原路径、大小、SHA-256、审计检查点；数据库、对象、未完成上传及原审计链段均加密。校验拒绝额外根目录或密文条目。密钥不进入副本。外部仍可见备份编号、时间、密钥编号、条目数量和近似大小，不隐藏全部元数据。

维护列表读取已发布副本的元数据，不在每次刷新时重验全部密文。创建完成时已完整校验；另存或使用前仍应通过离线 `verify` 核对介质内容及可信检查点。

复用现有维护屏障、完整清单、原审计链段、独立检查点和只写全新目录的恢复。加密副本保留容量、份数、物理余量及失败副本占用保护；预算计入密文、标签和清单，旧明文副本也占预算。SQLite 快照及校验需要临时明文数据库：服务端放在受保护的数据根目录内、加密副本之外；离线工具默认用系统临时目录下的私有子目录，可用 `--temporary-dir` 指向已有受信任目录。临时目录应有足够空间，不得位于源备份中；文件为 0600，目录为 0700。正常及可处理异常结束清理，进程强退后的残留仍须按敏感数据处理。

恢复先完成全部标签、摘要、数据库完整性、对象/任务和审计校验，再创建目标，缺钥或错钥不产生恢复目录。流式解密在标签最终通过前的输出只进入私有临时目录或带 `.restore-incomplete` 的新目标，不向业务提供。恢复故障保留不可启动标记，不覆盖业务卷；实际路径检查也拒绝经链接父目录写回源备份。磁盘崩溃、恶意宿主机或并发改写介质不属于可保证范围。

## 本机命令与保管

以下为开发环境示例。`--data-dir`、`--backup-dir` 应与实际服务配置一致；自定义密钥父目录须预先由维护者建立并保护。容器命令用 `node build/scripts/maintenance.js` 替换 `npm run maintenance --`，默认路径分别为 `/data/store`、`/data/store.backups`、`/data/store.backup-keys`。

```powershell
npm run maintenance -- keys-init --key-file .local/data.backup-keys --data-dir .local/data --backup-dir .local/data.backups
npm run maintenance -- keys-status --key-file .local/data.backup-keys --data-dir .local/data --backup-dir .local/data.backups
npm run maintenance -- keys-rotate --key-file .local/data.backup-keys --data-dir .local/data --backup-dir .local/data.backups
```

初始化只用于已确认没有旧加密副本的部署。密钥缺失且指定备份目录存在加密副本或加密未完成副本时，工具返回 `BACKUP_KEY_RESTORE_REQUIRED`，应找回原密钥；不要另指定空备份目录绕开检查。命令仅输出密钥编号和数量，不输出材料。轮换成功后服务下次创建副本自动读取新密钥，无需重启；原副本仍用保留的旧密钥。

初始化后刷新管理员“存储与维护”，应显示“新备份加密已就绪”。可从页面或原 HTTPS/WSS 维护命令创建副本；网页不下载密钥、备份内容，也不执行密钥轮换。备份及完整密钥文件应由部署维护者**分别**复制到独立受保护位置。密钥材料不能写进命令参数、聊天、源码或公开报告；`.backup-keys` 及其锁/临时文件均被提交和构建排除。

对已经复制到本机的副本，以实际编号和可信检查点替换占位：

```powershell
npm run maintenance -- verify --source .local/backup-copy/backup-实际编号 --key-file .local/protected/data.backup-keys --anchor .local/independent-checkpoints/checkpoint-实际序号-实际摘要.json
npm run maintenance -- restore --source .local/backup-copy/backup-实际编号 --target .local/restore-new --key-file .local/protected/data.backup-keys --anchor .local/independent-checkpoints/checkpoint-实际序号-实际摘要.json
```

备份密钥用于解密副本；恢复后若有已启用 MFA 的账号，启动还需另行提供对应 `MFA_KEY_FILE`。两种密钥不能互相替代。离线读取旧格式 1 需要显式加 `--allow-plaintext yes`；不自动重写或删除旧副本，不提供服务端新建明文备份的开关。

## 已验范围与限制

宿主机 Node 24.22.3：39 项检查、139 个业务安全场景通过，含新增加密 TLS/WSS 八场景；编译后七组探针通过。覆盖正常恢复、零字节/多分块、缺钥/错钥/删去旧钥、清单和密文篡改、条目互换/降级、旧副本兼容、失败占用、轮换及原数据保留。Unix 权限和符号链接断言由 Linux CI 待验，本机 Windows 未执行其专用分支。Edge B36～B40 直接观察缺钥、初始化后刷新、两次创建、轮换新旧编号、三份上限及普通用户无入口；三份夹具副本另由本机工具恢复验证，不称为网页恢复。

本轮版本 9 脚本已增加最终运行时内七组隔离探针、部署密钥持久化比较、复制后的加密备份校验/恢复。PowerShell 5.1 静态配置通过；实际 CI/镜像扫描和使用者本机原卷升级仍待完成，之前版本 8 成功不能替代它们。

密钥文件必须另存到独立受保护位置，轮换后重新保存完整密钥文件；备份介质和密钥不应由同一份复制一起分发。丢失旧密钥后无法从相应加密副本恢复。它保护脱离受信任主机的副本，不是业务文件静态加密、端到端加密、HSM/KMS 或受感染主机防护。首版仍为单进程、完整审计保留、不自动删旧/失败副本，不提供自动密钥过期或介质安全擦除。新机制不会追溯加密原有明文副本。

依据：[Node 24 crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html)、[NIST GCM 规范](https://csrc.nist.gov/pubs/sp/800/38/d/final)。
