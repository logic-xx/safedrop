## 应用运行时修补

仅将 Node 基础版本升至 24.22.3 的同发行版镜像，仍有 45 条高/严重记录，因此采用以下打包修补，后续真实 CI 及本机验收已通过对应范围：

- 构建使用按摘要固定的 Node 24.22.3；生产依赖从构建结果裁剪，开发依赖不进入运行时。
- 运行时使用按摘要固定的 Google Distroless Node 24 / Debian 13 非 root 镜像，移除运行时 npm、shell 和多余系统工具。基础镜像与最终应用镜像分别扫描，实际 Node 版本另由运行探针核对。
- 保留 UID/GID `10001:10001`、`/data` 挂载、`/data/store` 数据及 `/data/store.mfa-key` 默认位置；保留 Compose 的只读根、权限、网络、端口和资源限制。不对已有卷做 chown、清库或重建。
- 通过 `server/runtime.ts` 先完成现有初始化，再加载服务；使用镜像内 Node 作为入口。维护命令继续使用 `docker compose exec app node ...`；镜像不再提供 `sh` 或 `npm` 交互命令。
- CI 中复用 `verify-container.ps1`，实际运行隔离容器，检查严格 HTTPS/WSS、权限、账号/文件/配额/交付、MFA、重启与备份恢复；随后扫描同一 `safedrop:verify` 镜像。仅将脱敏汇总放入 `reports/ci`，不发布生成的账号、私钥或备份。
- 容器 MFA 探针核对实际 Node 24 至少为 24.22.3，并把版本记入结果；旧容器报告缺少该证明时，新的 CI 运行时汇总不会沿用旧成功。

此前本地已用官方校验和验证的便携 Node 24.22.3 完成构建、27/27 测试、编译后入口初始化/严格 HTTPS/重启账号保留和五组 MFA 探针；没有修改系统 Node 安装。前端仍为 `index-7EgnN7Bg.js`。这些宿主机证据与后续真实 CI、旧卷升级分别记录。第一次入口辅助检查误用了数据库文件名，修正辅助脚本后复验成功；产品数据库文件和路径没有更改。

本次按“提交并手动推送 → CI 隔离运行及扫描 → 使用者本机原卷升级 → 工具补核入口”的顺序取得结果；没有先部署未验证候选。当前本机已升级新应用运行时，网关保留原版本和原 CA。后续运行时改动继续执行对应验证，纯文档更新无需重做本次容器验收。

当前本地网关仅配置内部证书和反向代理，没有配置接收用户 JWK 或 HTML 模板解析；这用于评估暴露面，不能单凭配置就断言组件完全不受影响。上述两项高风险已由本轮实际 CI 镜像及本机版本 8 修补验收，前两轮失败报告保留；不添加通配例外、不使用 `--ignore-unfixed`、不把未验证假设写成通过。
